# NEAR Hunt review rubric

Built from the official brief, https://nearhackathon.com/HACKATHON.md (fetched 16 Nov 2026), whose
Q-017 sets the role of AI review: **screening, not deciding** — reproducibility check, feature
verification, structured report, preliminary score. Humans decide; a low score alone never rejects.

This file is the shared memory of what the owner cares about. When the owner gives feedback that
generalises ("a wallet button over a Web2 app is not integration"), it is added here as a rule under
the criterion it refines, with the date, so every later assessment applies it.

## Part A — Eligibility checks (pass / flag / fail, never a score)

Each check cites evidence. `flag` means a human should look; only the brief's hard rules can `fail`.

| Check | Rule (brief) | How to check |
|---|---|---|
| `window` | Code from **2026-10-19** to **2026-11-14T23:59Z** is judged; earlier commits are baseline (Q-001) | `git log` dates; commits after the deadline noted separately |
| `prior_work_separated` | An old project as-is is not eligible; a new feature on it is, if separated by branch or tags `pre-hackathon` / `hackathon-submission` plus a README diff link (Q-003, Q-004) | Pre-window history present? Separation present? |
| `other_chain_disclosed` | An existing product on another chain is allowed; **only the NEAR integration built in the window is judged**; must be disclosed in the README (Q-002) | README disclosure; score only the in-window NEAR work |
| `libraries_disclosed` | Templates, boilerplate, own old libs and AI-written code are allowed but must be listed in the README; own old libs count as baseline (Q-005) | README section; large imports in the first commit |
| `multi_project` | One person, at most 2 projects, independent, and each README names the other (Q-015). Not the same project twice | Same people/repos across submissions (the graph), README cross-reference |
| `repo_public` | Repository public through judging (Q-014) | `git ls-remote` |
| `license` | A LICENSE file (Q-014) | file present |
| `demo_post` | Public X post: says built at NEAR HACKATHON, tags @NEARProtocol and #NEARHackathon, has video or screenshots (procedure §2) | fxtwitter |
| `reproducible` | README gives "do X — see Y" steps a judge can follow; local-only demo needs public repo + reproducible README + video (Q-012, §1) | README read |

## Part B — Scores (1–5, each with evidence; `null` with a reason when it could not be judged)

Anchors: **1** absent or false · **2** weak · **3** solid core · **4** strong · **5** exceptional.

1. **Authenticity — is it what it says it is?** Claims from the post and description checked against
   code and chain. 1 = headline claims not in the code, or mocked; 3 = core claims real, some
   overstated; 5 = every checked claim found, verified on chain or by a reproducible path.
2. **Originality — idea and execution.** Against prior art *and against the other submissions*
   (use the graph: similar pitches, shared code, same team). 1 = copy, fork or template with a new
   README; 3 = familiar idea, own implementation; 5 = a new mechanism nobody else in the set built.
3. **Technical implementation — what was built in the window, and how well.** Difficulty, correctness,
   structure, tests, security of key handling. Pre-window code does not count (Part A).
4. **NEAR integration — is NEAR load-bearing?** 1 = wallet button or unused dependency;
   3 = a contract or NEAR call the product needs; 5 = the product cannot exist without NEAR-specific
   features (Intents, Chain Signatures, function-call keys, sub-accounts, NEAR AI / TEE, FastData…)
   used correctly. Testnet-only is fine (Q-010).
5. **Track fit — judged on the track's own words** (the `Build` column and its "Judged on…" line,
   e.g. games: *the game loop, not the token*; memecoins: *the mechanic, not the chart*; thesis:
   *the evidence, not the conviction*). Score against the best-fitting declared track; name it.
6. **User experience and reproducibility — can a judge try it?** 1 = cannot be run or opened;
   3 = runs from the README or a working hosted demo; 5 = polished, live, obvious first use.
7. **Impact — would anyone use it?** Real users or on-chain activity not generated by the team,
   a clear user and problem, "something a normal company could use tomorrow" where the track asks.

### Calibration (added 16 Nov after the DeepSeek pilot gave 5s to most projects)

- **Start every score at 3 and move only on evidence.** Write the evidence that moved it. Across the
  whole set, 5s should be rare: a 5 names what makes this project exceptional *compared with the other
  submissions*, not just "it works".
- **Activity only by the team's own accounts caps `impact` at 2** and `completeness` at 4.
- **`near_integration: superficial` or `none` caps the `near_integration` score at 2 and `track_fit`
  at 3**, and for an existing product from another chain (Q-002) `technical` and `completeness`
  score only the in-window NEAR work, not the product around it.
- **Any headline claim not found in the code caps `authenticity` at 3; two or more cap it at 2.**
- Scores must agree with the verdict and the red flags. If the verdict says the NEAR part is a side
  rail, no NEAR-related score is above 2.

`preliminary_score` = unweighted mean of the scored criteria, one decimal. Weights are the owner's
decision and are not set yet.
